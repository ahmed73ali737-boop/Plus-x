# طلبات الحسابات — المرحلة الأولى

> تحديث: هذه الوثيقة تصف خط الأساس السابق. السلوك الحالي للاعتماد والموافقة والتعيين موثق في `ACCOUNT_APPROVAL_WORKFLOW_AR_20261021.md`؛ التسجيل بالهاتف لا يستخدم OTP ويظل طلباً قبل الموافقة.

مرجع التنفيذ: `IMPROVEMENT_AND_DEVELOPMENT_PLAN_AR_2026-10-21.md`، المرحلة 1.
مرجع السياق: `FUNCTIONAL_UX_ANALYSIS_AR_2026-10-21.md`.

## نطاق هذا التغيير

إضافة نموذج تخزين مستقل ومساعدات حفظ وقراءة داخلية. لا توجد واجهة HTTP جديدة، ولا خدمة موافقات، ولا تحويل لمسارات إنشاء الحسابات في هذه المرحلة. الحسابات الحالية ومسارات الإنشاء الحالية مستمرة بسلوكها السابق إلى مرحلة توحيد المسارات؛ لذلك لا تعد سياسة الاعتماد مكتملة على مستوى المنتج بعد.

طلبات الجدول الجديد لا تنشئ مستخدماً أو جلسة أو عضوية أو تكليفاً. لا يتغير سجل الشخص، ولا تنقل إليه دعوات الضيوف أو RSVP أو QR. الترحيل لا يعتمد الطلبات القديمة تلقائياً ولا يعيد تجزئة كلمات مرور المستخدمين الحاليين.

## نموذج التخزين

- الجدول: `px_account_requests`؛ الترحيل الإضافي: `ops/013_account_requests.sql`.
- الحالات: `pending`, `approved`, `rejected`, `expired`, `cancelled`.
- هوية الطلب: البريد الموحد، الاسم، الهاتف الاختياري، الدور المطلوب، المصدر، ومفتاح الطلب الفريد.
- نطاق الطلب: `scope_type` و`scope_id`، مع ربط أجنبي صريح إلى مساحة الموقع أو المؤسسة. تحفظ مراجع الفعالية والشخص والمشاركة عند الحاجة.
- الإسناد المطلوب بيانات غير فعالة: `membership_role` و`assignment_role`؛ لا تنشأ الصفوف المقابلة.
- الإشراف: `supervisor_id` مطلوب، ومقدم الطلب والمراجع ووقت القرار والسبب والانتهاء حقول منفصلة.
- يمنع الفهرس الجزئي طلبين معلقين للبريد والنطاق نفسيهما، حتى إذا اختلف الدور. يمكن طلب نطاق آخر أو تقديم طلب جديد بعد إغلاق السابق.
- التخزين يقبل تجزئة scrypt فقط عبر مساعد الإدراج. كلمة المرور مدخل عابر ولا تحفظ بنصها؛ القراءة العامة تستبعد التجزئة ومفتاح منع التكرار، ولا توجد بيانات JSON حرة في هذا الجدول.
- لا تسمح قيود قاعدة البيانات ببقاء التجزئة بعد حالة نهائية، أو رفض بلا مراجع ووقت وسبب. تنفيذ الانتقالات والتنظيف الفعلي يأتي مع خدمة المرحلة الثانية.
- يمكن ترك التجزئة فارغة لطلب قديم أو لتدفق تعيين كلمة المرور لاحقاً. لا يوجد رابط تعيين أو مزود إرسال منفذ في هذه المرحلة.

هذه قيود سلامة بيانات، وليست تفويضاً لإنشاء حساب أو منح دور. اختيار المشرف الصحيح، والتحقق من صلاحية المراجع والنطاق ومنع الاعتماد الذاتي، مسؤولية خدمة المرحلة التالية؛ لا يستقبل مساعد التخزين body من أي endpoint حالياً.

## تشغيل التحقق

SQLite، دون بيانات فعلية:

```bash
python -m pytest -q tests/test_account_requests_model.py
```

PostgreSQL: اضبط `PX_ACCOUNT_REQUEST_TEST_DATABASE_URL` لقاعدة اختبار مخصصة ثم شغل الاختبارات نفسها. ينشئ الاختبار schema عشوائياً ويحذفه بعده، ولا يعدل جداول public. لا يوجد رجوع إلى SQLite عند طلب PostgreSQL. يتولى job `postgres-native` تشغيل ذلك وحفظ `qa/account-requests/postgres-junit.xml` ضمن أدلة CI المرتبطة بالمصدر.

لا تشمل هذه المرحلة اعتماداً إدارياً أو إطلاقاً إنتاجياً. الانتقال إلى خدمة الاعتماد يحتاج تأكيد المستخدم بعد مراجعة نتيجة المرحلة الأولى.
